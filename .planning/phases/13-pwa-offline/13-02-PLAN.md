    **Part A — Create `src/services/sync.ts` (Sync Engine):** (per D-09: full offline experience, D-11: create/edit queued)

    Export a `SyncService` class with methods:

    - `static async replayQueue(): Promise<{ succeeded: number, failed: number, conflicts: ConflictRecord[] }>`
      1. Load all pending operations from `db.syncQueue.toArray()` ordered by `createdAt`
      2. For each operation:
         - Send the API request using `fetch()` (not Axios, to avoid the offline interceptor) with:
           - `method`: op.method
           - `headers`: `{ 'Content-Type': 'application/json', 'X-XSRF-TOKEN': getCookie('XSRF-TOKEN'), 'X-Sync-Engine': 'true' }`
           - `credentials: 'include'`
           - `body`: JSON.stringify(op.payload) (skip for DELETE)
         - If response is 200/201/204 → call `db.syncQueue.delete(op.id)` → increment succeeded
         - If response is 409 (conflict per D-19):
           - Parse response body for `{ serverVersion, baseVersion }`
           - Call `detectAndStoreConflict(op, serverVersion, baseVersion)`
           - Delete the op from syncQueue (conflict now stored separately)
         - If response is 401 → throw `new SyncAuthError('Session expired')` → caller pauses queue
         - If response is 5xx → increment retry, update lastError → continue to next op
         - On network error → increment retry, update lastError, break (stop processing further)
      3. Return summary object

    - `static async detectAndStoreConflict(op: PendingOperation, serverVersion: Record<string, unknown>, baseVersion: Record<string, unknown>)`
      1. For each field in op.payload that differs from serverVersion:
         - If field exists only in local (payload) or only in server, include the diff
         - If field value differs between local and server → it's a conflict
         - If field is same in both → no conflict for this field
      2. If ALL conflicting fields have same local value as base (the user didn't change it, server did) → auto-resolve by updating local cache with server version
      3. If some fields conflict → create conflict record in `db.conflicts` with:
         - `entityType`, `entityId`, `localVersion` (op.payload), `serverVersion`, `baseVersion`
         - `status: 'pending'`, `detectedAt: new Date().toISOString()`
      4. If no conflicting fields (different fields changed per D-21):
         - Auto-merge: merge local payload into server version, send merged PUT request
         - If merge succeeds, update local cache with merged result

    - `static async autoResolveStaleConflicts(days: number = 7)` — per D-22
      1. Query `db.conflicts` where `status === 'pending'` and `detectedAt` older than N days
      2. For each stale conflict: resolve as 'keep-server' (last-write-wins), update status to 'resolved', update local cache
      3. Return number of auto-resolved conflicts

    - `static async resolveConflict(conflictId: number, resolution: 'keep-local' | 'keep-server' | 'manual-merge', mergedPayload?: Record<string, unknown>)` — per D-20
      1. If `keep-local`: send PUT with localVersion to server, update local cache
      2. If `keep-server`: update local cache with serverVersion
      3. If `manual-merge`: send PUT with mergedPayload, update local cache
      4. Update conflict status to 'resolved' with `resolvedAt` and `resolution`

    - Helper: `static getCookie(name: string): string | null` — reads from `document.cookie`

    - Export class `SyncAuthError extends Error` for session expiry signaling

    **Part B — Create `src/stores/sync.ts` (Pinia Store):**

    Per D-06 (visual indicator), D-07 (manual sync), D-08 (indicator disappears), D-10 (last sync timestamp):

    Use `defineStore('sync', () => { ... })` with setup syntax:

    **State:**
    - `pendingCount: ref(0)` — number of pending operations in syncQueue
    - `lastSyncAt: ref<string | null>(null)` — ISO timestamp of last successful sync (persisted in db.syncMeta)
    - `isSyncing: ref(false)` — true while manual sync is in progress
    - `isOnline: ref(navigator.onLine)` — reactive connectivity state (also synced from useOnline)

    **Actions:**
    - `async refreshPendingCount()` — sets `pendingCount.value = await db.syncQueue.count()`
    - `async loadLastSyncAt()` — reads `lastSyncAt` from `db.syncMeta.get({ key: 'lastSyncAt' })`
    - `async manualSync()` — per D-07:
      1. if `isSyncing.value` → return (prevent concurrent syncs)
      2. set `isSyncing.value = true`
      3. call `SyncService.replayQueue()`
      4. call `SyncService.autoResolveStaleConflicts(7)` — per D-22
      5. call `refreshPendingCount()`
      6. update `lastSyncAt.value = new Date().toISOString()` and persist to `db.syncMeta.put({ key: 'lastSyncAt', value: lastSyncAt.value })`
      7. set `isSyncing.value = false`
      8. if conflicts detected during sync, set `hasConflicts.value = true`
    - `async dismissConflict(conflictId: number, resolution: 'keep-local' | 'keep-server')` — convenience wrapper

    **Getters:**
    - `hasPending: computed(() => pendingCount.value > 0)` — D-08 (indicator hides when 0)
    - `pendingLabel: computed(() => \`${pendingCount.value} opera\u00e7\u00f5es pendentes\`)`

    **Setup:**
    - On store initialization, call `refreshPendingCount()` and `loadLastSyncAt()`

    The store is a singleton (Pinia convention) imported via `useSyncStore()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Sync Queue → Laravel API | Queued operations replayed with potentially stale XSRF token |
| Conflict Dialog → User | User selects which version to keep; must be validated server-side |
| UpdatePrompt → SW | Update triggers SW lifecycle; user must confirm to avoid data loss |
| IndexedDB → Pinia Store | Stores read from Dexie; liveQuery subscriptions create reactive bindings |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-06 | Spoofing | Sync queue replay with stale session | high | mitigate | SyncService catches 401, throws SyncAuthError, pauses all further replays. User re-authenticates before resume. The `X-Sync-Engine: true` header prevents re-interception by api.ts interceptor. |
| T-13-07 | Tampering | Conflict resolution user choice | medium | mitigate | Server validates all write operations regardless of client-side merge choice (D-20). Conflict resolution only selects which payload to send; server applies its own validation. |
